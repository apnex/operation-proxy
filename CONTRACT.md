# operation-proxy

The contract of record for operation-proxy: what a consumer can depend on, admitted to zorg's component set by the director's ruling `D29` in zorg's `docs/DECISIONS.md`, and named by its `D30`; its vision is ratified (zorg's `D50`), and this contract is a draft until its capabilities are built and verified.\
It also carries the fields of a mission-kit registry entry, and that entry is generated from this file, never written as a second copy.\
Admitted to mission-kit's component registry as `C8`, its first release `0.1.0` (`docs/DECISIONS.md` `D8`); its frontmatter is the entry's.

**Status: its design certified at zorg's Delta 1, stage 0, for amendments 1 and 4 (`E13`); provisional until stage 4a builds it.**

---

## Duty

Let short-lived processes invoke named operations through one long-lived caller they share, each invocation still ending honestly.

---

## Contract

What a consumer can depend on, one capability per row.\
A capability is named for what it offers, not for who offers it, so two components that provide the same capability share its name, and the overlap is visible.\
**Provides** means this component implements the capability; **carries from X** means it passes X's capability through its own interface.\
**Requires** names the capabilities of other components a row depends on, as `component:capability`, so a census can follow an application's demand down through the components it reaches.\
The trait column names any trait a system takes on by using the capability.

| Capability | Relation | Requires | What a consumer can depend on | Trait |
|---|---|---|---|---|
| `proxied-invocation` | provides | `operation-call:honest-call-ending`, `operation-call:caller-chosen-bound`, `operation-call:invocation-identity`, `operation-call:request-correlation`, `operation-call:call-refusal`, `operation-call:answer-in-parts`, `operation-call:cancel-invocation`, `shape-check:plain-json-value` | A short-lived process invokes a named operation through the proxy and gets exactly one ending, within the bound it chose, kept across the hop: the ending of the direct call the proxy makes for it, with a bound a hop allowance shorter (`PX5`), unchanged, when it reaches the process before the bound passes, refused `not-sendable`, or `unknown` with `bound-passed`, as the call layer's caller ends it, when the client half's own checks end it with nothing written (`PX5`), not delivered with the proxy's code when nothing of the invocation was handed on (`PX6`), and otherwise unknown - never an answer, never not delivered - with the hop's reason and no AGP code or delivery report, both where the hop loses certainty and where the call layer's ending has not been produced or carried back by the process's own bound; an invocation's identity is the same through the proxy as in a direct call, an invocation whose process has gone is finished and its ending dropped, and the proxy never repeats an invocation on its own. | none |
| `caller-interface-parity` | provides | `operation-call:honest-call-ending`, `operation-call:caller-chosen-bound`, `operation-call:invocation-identity` | The client half offers the caller interface the call layer offers, so code written against the call layer runs through the proxy unchanged. | none |
| `proxy-on-demand` | provides | none | A proxy is there when the first process of an application, identity and target needs it, with nothing set up beforehand: on a machine `PX2` serves, processes that start at once end with one proxy, and a proxy left behind by a crash is replaced; in a browser, the browser keeps one per application, identity and target. | none |
| `proxy-idle-expiry` | provides | none | A proxy on a machine ends itself after an idle time the application states, and never ends itself while an invocation it carries is in flight; in a browser, the browser ends it after the last page that uses it. | none |
| `one-identity-per-proxy` | provides | none | Each proxy carries one application's invocations under one identity to one target, through one caller of the call layer and its one connection, invocations from processes running at once carried at the same time, and never carries a process's invocation under another identity. | none |
| `host-local-proxy-channel` | provides | none | A proxy is reached only over a channel local to its host, never over the network, which processes may reach it is decided by the host's own access rules on that channel, and a client half can query the proxy's status over that channel (`client.status({ timeMs, signal? })`) without starting a proxy when none is running. | none |

The component holds nothing across a restart, coordinates no actors and contains no model, so none of its capabilities brings a trait.\
The processes one proxy serves act under one identity, so sharing it does not make a system multi-agent.

The channel and the hosting are adapters: an operating-system process and a local socket on a machine, and a browser's shared worker and message ports (zorg's `D31`, `D57`); the design is below.

## Proxy design

**Maturity: provisional**, designed under zorg's Delta 1, amendment 1, and zorg's rulings `D28` to `D31` and `D34`, its answers in parts and cancelling under zorg's Delta 4, stage 6 (`D64`).\
Each declaration names the exit criterion of zorg's `docs/DELTAS/DELTA-1.md` that proves it and the test that exercises it.\
The call layer is operation-call; its endings, bound, abort signal and invocation identities are those of zorg's `docs/ARCHITECTURE-TARGET.md`, `EM11` and `EM12`.

**PX1 - Keys, halves and adapters.**\
A proxy serves one key: an application and an identity, each matching `^[a-z0-9][a-z0-9-]{0,62}$`, and a target, a string of 1 to 2048 characters naming what the proxy's caller connects to.\
The key's digest is the first 16 lowercase hexadecimal digits of the SHA-256 of the UTF-8 bytes of `<application>\n<identity>\n<target>`.\
The proxy half runs in the proxy process and holds one caller of the call layer, which the application builds from the key; the client half runs in each short-lived process and offers the call layer's caller interface.\
Hosting and the channel are adapters: the machine adapter for Linux - an operating-system process, a Unix domain socket for the channel, and an exclusive kernel lock on `<digest>.lock` inside the user's private runtime directory for ownership (`D57`, `D58`) - and the browser adapter of `PX8` (`SharedWorker` and `MessagePort`, `D57`) are both built.\
Tested by: `E17`, in `test/contract/one-identity-per-proxy.test.js`, with a fixture application, including two keys differing only in target, which get two proxies, and one key used from 20 processes, which gets one.

**PX2 - Where a proxy is found on a machine (`D57`, `D58`).**\
The runtime directory is `.operation-proxy` in the user's home directory as the system's user database records it, never as an environment variable says, so every process of the user on the host agrees on it; a channel socket path that would be longer than 107 bytes is refused, ending the invocation `not-delivered` with `proxyCode` `runtime-dir-unsafe`.\
The client half and the proxy alike create it with mode `0700` when it is absent, and refuse one that is not a directory - a symbolic link to one included - is not owned by the user, or grants any permission to the group or to others, ending the invocation `not-delivered` with `proxyCode` `runtime-dir-unsafe`.\
In it, the file `secret` holds 32 random lowercase hexadecimal digits and a newline: a process finding no `secret` writes a complete one, with mode `0600`, to `secret.<16 random hexadecimal digits>`, links that file to `secret`, which succeeds for one process only, and removes its own file, so `secret` only ever appears whole; every process then reads `secret`, and one that is not exactly 33 bytes of that form, or is not a regular file - a symbolic link included - ends the invocation `not-delivered` with `proxyCode` `runtime-dir-unsafe`.\
A key's channel is the socket `<runtime directory>/<digest>.sock`, and its ownership is the exclusive kernel file lock on `<runtime directory>/<digest>.lock` (mode `0600`, regular file, never a symbolic link), both inside the mode-`0700` runtime directory (`D57`, `D58`, retiring `BL22`).\
So only the user's own processes can reach a proxy or hold its ownership lock, since no other non-root user can traverse the mode-`0700` runtime directory (`EACCES`), no abstract-namespace socket is bound in `/proc/net/unix`, and no proxy listens on the network.\
Tested by: `E17` and `D3-E2`, in `test/contract/host-local-proxy-channel.test.js`, which checks the modes, refuses a directory open to others, a malformed `secret` and a symbolic link at `<digest>.lock`, finds one proxy for commands of one key run with different `HOME`, `TMPDIR` and `XDG_RUNTIME_DIR` settings, finds no listening network port and no `operation-proxy-` abstract-namespace socket in `/proc/net/unix`, starts 20 first-ever clients at once, and a client killed before and after linking, each leaving one agreed secret, and verifies that holding the exclusive lock on `<digest>.lock` keeps a proxy from starting (`proxy-unreachable`) until the lock is released, when the next command starts a proxy.

**PX3 - Owning a proxy, exactly once, on a machine (`D57`, `D58`).**\
A proxy owns its key while it holds an exclusive kernel file lock on `<runtime directory>/<digest>.lock` (via Node's built-in `DatabaseSync` in `EXCLUSIVE` locking mode with `BEGIN EXCLUSIVE` and `timeout: 0`, which acquires an exclusive `fcntl` lock in the operating system across processes and an inode lock within the process, and which the operating system releases the moment the holding process ends, `SIGKILL` included).\
A starting proxy opens `<runtime directory>/<digest>.lock` (creating it with mode `0600` when absent, and refusing a non-regular file or symbolic link as `runtime-dir-unsafe`) and attempts the exclusive lock first; if the lock is held, another proxy of the key owns it (including one paused with `SIGSTOP`), and this starter closes its handle and exits with status 0, touching nothing.\
`<runtime directory>/<digest>.lock` is never unlinked on acquisition or release, so concurrent starters and exiting owners never race over unlinking or replacing the file.\
Only the owner touches the channel socket: it removes any socket file left at `<digest>.sock`, listens there, and then builds its caller; on a normal exit it closes and removes `<digest>.sock` before it closes its lock handle on `<digest>.lock`, and after `SIGKILL` the operating system releases the lock on `<digest>.lock` at once and the next owner removes the leftover `<digest>.sock`.\
The client half connects to `<digest>.sock`; when there is nothing to connect to, it launches the proxy with the command the application supplies, detached from itself and with its output discarded, and connects again every 100 milliseconds, launching again at most every 500 milliseconds, until the invocation's connect deadline.\
Tested by: `E17` and `D3-E2`, in `test/contract/proxy-on-demand.test.js`: 20 processes started at once leave one owner; a proxy killed with `SIGKILL` just after taking ownership, just after listening on the channel, and while serving, is each time replaced by the next command (and by 20 concurrent starters after `SIGKILL`) within zorg's default connect timeout of 5 seconds; a proxy paused with `SIGSTOP` keeps ownership, so no second proxy starts and a command ends `not-delivered` with `proxy-unreachable` at its connect deadline; a starter that loses never removes the channel socket.

**PX4 - The channel's messages.**\
The channel carries newline-delimited JSON in UTF-8, one message per line, each line at most 16785408 bytes with its newline - the largest request message the call layer sends, 16777216 bytes (`EM11`), and 8192 bytes for the channel's own fields; every message is an object holding `operationProxy`, which is 1, `type`, and the fields its type names:

| Direction | `type` | Fields |
|---|---|---|
| client to proxy | `hello` | `key`, holding `application`, `identity` and `target` |
| client to proxy | `status` | `key`, holding `application`, `identity` and `target` |
| proxy to client | `welcome` | none |
| proxy to client | `status` | `ready`, true or false; `connections`, a safe integer from 0 to 9007199254740991; `inFlight`, a safe integer from 0 to 9007199254740991; `target`, any plain JSON value (`null` when none) |
| proxy to client | `refused` | `code`: `key-mismatch`, `version`, or `admission-refused` (when `callerReady` resolves `{ refused: "admission-refused" }`, latching terminal startup refusal `PX9`) |
| client to proxy | `invoke` | `request`, a whole number from 1, new for each invocation on the connection; `invocation`, an invocation identity as `EM11` writes it; `host`; `service`, the name the operation is served under, matching the identity pattern of `PX1`; `operation`, the operation's own name, matching the same pattern; `input`; `deadline`, the moment the bound passes, as `PX5` writes it, a JSON string of decimal digits, since a reading in nanoseconds can pass the largest integer JSON carries exactly; `repeat`, true or false; `aborted`, true or false; `parts`, true when the call request gives `onPart` and false otherwise |
| client to proxy | `abort` | `request` |
| proxy to client | `end` | `request`; `ending`, the call layer's ending as `EM12` gives it, or the proxy's of `PX5` and `PX7` |
| proxy to client | `part` | `request`; `sequence`, a whole number from 1, the next for its request; `answer`, the part's answer as the proxy's call gave it |
| proxy to client | `alive` | `request` |

The client sends `hello` first on an invocation connection and nothing else until `welcome`, or sends `status` as the first and only message on a status probe connection (`PX5`, `PX6`); the proxy sends `welcome` only once its caller is ready by the application's own test (`PX9`), answers a valid `status` at once with `status` (`ready` true once `half.ready` has been called and while `stopInvocations` has not been called, `connections` counting welcomed and waiting `hello` connections, `inFlight` counting active calls, and `target` from `PX9`) before marking the status connection closed and closing its link (ignoring any pipelined or later messages on that connection), and answers a key other than its own, or a version other than 1, on either `hello` or `status` with `refused` and closes.\
A connection carries any number of invocations at once, and their messages arrive in any order, paired by `request`; an `abort` for a request already ended is ignored.\
A `part` and an `alive` go only for a request written with `parts` true, and only before its `end`, which follows every `part` of it (`PX5`); a part's line fits, since its answer reached the proxy within AGP's largest receive limit, 16777216 bytes (`EM11`), and its channel fields take less than 8192.\
A line that is longer, does not parse, or breaks this table closes the connection; breaking the table includes a first message holding `operationProxy` other than 1, which is refused `version`, a request number used twice on one connection, a first client message other than `hello` or `status` (or the browser adapter's `ping`, `PX8`), any client message after `hello` (other than `ping`, `PX8`) before `welcome`, any message after `status`, an `end` for a request the client never wrote or naming another invocation or operation, a `part` or an `alive` for a request the client never wrote with `parts` true or whose `end` it has read, a `part` whose `sequence` is not the next for its request, a `taken` anywhere but on a browser's port (`PX8`), and a field the table does not name.\
The proxy compares a `hello`'s or `status`'s key with its own exactly, string by string, and any difference is `key-mismatch`.\
The channel's version stays 1: a proxy started before `parts` joined `invoke`, and still running, closes a connection on its first `invoke`, so each invocation written on it ends `proxy-lost` until that proxy idles out or is stopped, a named cost of the change, since zorg has no release yet whose proxy could be left running.\
Tested by: `E17`, in `test/contract/proxied-invocation.test.js`; `D4-E6`, in the same file, where a `part` out of order, a `part` and an `alive` for a request written with `parts` false, for one never written and for one whose `end` was read, each close the connection, every invocation written on it and undecided ending `proxy-lost` and the parts already given to `onPart` standing; and where consecutive parts in order read for an invocation already decided are discarded, while a part out of order read for it closes the connection, another invocation written on it ending `proxy-lost` and the decided one unchanged; and `D8-E1`, in the same file, where an initial `status` is answered and closed, a `status` sent after `hello` closes the connection, and a `status` reply with fractional, negative or unsafe `connections` or `inFlight` closes the link and resolves `proxy-unreachable`.

**PX5 - Preparing, status, the bound, and when a proxied call is made.**\
The client half offers the call layer's caller interface, and two more steps: preparing - connecting, sending `hello` and receiving `welcome`, until a deadline the caller gives - and `status({ timeMs, signal? })` (`PX6`, zorg's Delta 8, `BL18`), which inspects the proxy's status over one probe connection without ever calling `connector.launch()` or retrying.\
Before it writes an invocation, the client half reads its clock first and then validates the call request and snapshots its `input` once through `operation-call`'s `readCallRequest` (`D55`), and applies the call layer's own checks on the caller's side (`EM11`) - numbers, depth, and a request message of at most 16777216 bytes, measured through `shape-check`'s `plain-json-value`, the request of a call accepting parts holding the `aliveWithinMs` the call beneath carries when the proxy makes it at once, the greater of 1 and half of the bound less the allowance, rounded down - ending one that fails them exactly as the call layer would, refused as `not-sendable`, so every invocation it writes fits a line; it refuses as the call layer does, with `EM9`'s `not-sendable` record exactly and an attempt identity it makes as `EM11` writes it.\
It reads its clock again once those checks are done, and when the caller's deadline has passed by then, it ends the invocation as the call layer's caller does - `unknown` with `bound-passed`, its attempt identity, and `agpCode` and `deliveryReport` `null` - with nothing written, so a deadline passed while checking wins over a refusal the checks found, for a prepared client half and an unprepared one alike.\
A host so long that the invocation would not fit a line - never one AGP accepts as a node name - is refused `not-sendable` too, where a direct call would meet AGP's own refusal.\
An invocation's bound starts when the caller invokes, as `EM12` says; when the client half is not prepared then, preparing happens within that bound, and a connection lost between invocations is prepared again within the next invocation's bound, so a find's pages keep the one deadline `EM10` gives them.\
The client half keeps its own deadline - the moment the caller's bound passes - and gives the proxy's call a deadline a hop allowance sooner: the application's allowance (`PX9`), by default 50 milliseconds, or half the caller's bound if that is less, rounded down to a whole millisecond.\
So an invocation through the proxy ends exactly as the direct call the proxy makes for it ends (zorg's `D48`): that call is made when the proxy hands the invocation on, with the abort signal as the proxy relays it, and with a bound ending at the sooner deadline - on a machine; in a browser, `PX8` - rounded down to a whole millisecond, so its own deadline falls between the allowance and the allowance plus less than 1 millisecond before the client half's deadline - a call that runs out its bound decides there, and one answered or refused sooner decides when that happens.\
Every event that call meets after its own bound - an answer, a refusal, a delivery report - is one it does not take; and an abort the process gives reaches it only when the relayed `abort` arrives, so an abort that crosses the hop while the send is being admitted may arrive after admission, where it cancels the invocation as `EM12` says, the call sending one `cancel` and ending by the host's end or at its deadline, which the abort fixed.\
Its ending is taken whenever the client half reads it before its own deadline, and an `end` read at or after that deadline loses (`PX6`); a return transit shorter than the allowance is enough for that, not required, since an ending decided early, or a deadline floored short of the allowance, leaves more time; an allowance of 0 - an application's own, or a bound of 1 millisecond - leaves no margin, and such an invocation may end `hop-stalled`.\
The rule applies to each invocation by its own deadline and its own allowance, so a find's pages each keep it, each page's bound being the time `EM10` leaves it.\
On a machine, the client half sends as `deadline` that sooner deadline, on Linux's `CLOCK_MONOTONIC`, in nanoseconds, as Node's `process.hrtime.bigint()` gives it, written in decimal: one clock for every process on the machine, which a change to the wall clock does not move.\
The proxy hands each invocation to its caller as it arrives, keeping no backlog: addressed to the endpoint `<service>/<operation>` on its host, with its operation's name, its invocation identity, its repeat flag, a bound of `deadline` less the proxy's own reading of that clock, rounded down to a whole millisecond and at most 2147483647, an abort signal that is already fired when `aborted` is true and that the proxy fires on `abort`, and, when `parts` is true, the `onPart` below.\
When less than 1 millisecond is left as the invocation arrives, the proxy does not hand it on, and answers `end` with `not-delivered`, `proxyCode` `deadline-passed` - the ending of a direct call that could not be made with a bound of a whole millisecond - so a bound of 2 milliseconds with an allowance of 1, whose sooner deadline leaves 1, is refused so whenever the hop takes any time at all, while with an application allowance of 0 it can be made.\
The client half writes `parts` true exactly when the call request gives `onPart`, which `readCallRequest` reads once with the other fields; it sends no `alive` of its own, since the proxy's call sends the caller's `alive` to the host (`EM12`), and the connection - in a browser, the port's `ping` (`PX8`) - tells the proxy the client is there.\
For an `invoke` whose `parts` is true, the proxy gives its call an `onPart` that writes each part it is given as a `part` of the request, at once and in order, with the `sequence` and `answer` the call gave it; and from the moment it hands the invocation on until that call's ending is sent or dropped, or the connection closes, it writes an `alive` for the request whenever the greater of 1 millisecond and half the bound it gave the call, rounded down, has passed on its clock since it handed the invocation on or last wrote a `part` or an `alive` for it, a timer that wakes late writing one and counting on from it.\
For an invocation written with `parts` true, the client half's own deadline is a deadline on signs of life: it starts at the bound after the caller invoked, and each `part` or `alive` read before it moves it to the bound after the moment it was read, on the client half's clock; one read at or after it is not taken and moves nothing, as an `end` read then is not (`PX6`).\
The `deadline` the client half sends is still the sooner deadline above, the bound less the allowance after the caller invoked, so the bound the proxy computes from it is its call's bound on signs of life, which each part and `alive` that call takes moves (`EM12`); a part reaches the client half only after the proxy's call has taken it, and the proxy's `alive` falls due at least every half of its call's bound while that call runs, rounded down, which for a call bound of 2 milliseconds or more is at most half of it.\
So the client half counts on a hop that keeps pace, an assumption rather than a property of every machine or browser: that while the proxy's call runs, no stretch of more than half that call's bound passes without the proxy writing a `part` or an `alive` - its timer waking in time - and that each `part`, `alive` and ending crosses to the client half in less than the allowance.\
On such a hop each sign of life is read before the deadline the one before it set, the deadline stays at least half the call's bound plus the allowance past the moment the call ends at its own deadline, and the call's ending is taken, as for a whole call; on a hop that falls behind, the client half's deadline may pass first and end the invocation `hop-stalled`, which says only that its ending is unknown, the later ending discarded (`PX6`).\
The client half gives each `part` it takes to `onPart` as `{sequence, answer}`, deeply frozen, at once, synchronously and in order, never awaited; what `onPart` returns or throws changes nothing, any native promise in it observed through `observePromises`; and a `part` or an `alive` is checked against `PX4`'s table first - written with `parts` true, its `end` not yet read, a part's `sequence` the next for its request, which a part that passes advances - and only then, when it was read for an invocation the client half has already decided, discarded, so a late part that breaks the table still closes the connection and changes no ending already decided.\
An abort bounds the deadline of an invocation written with `parts` true (zorg's Delta 4, amendment 4): from the moment the caller's signal fires, a `part` or an `alive` read before the deadline moves it to the bound after the abort and no further, and is still taken, a part given to `onPart`, so the invocation ends within one bound of the abort whatever the hop does.\
It does not fix the deadline as `EM12` fixes the caller's, since the client half's signs of life are the proxy's and its call's are the host's, and an `alive` the proxy wrote before the abort may be read after it; once the abort reaches the proxy, its call's deadline is at most its own bound after that moment (`EM12`), and on a hop that keeps pace the first sign of life read after the abort moves the client half's deadline to the bound after the abort, so that call's ending, decided at its deadline, is read before it whenever, besides, the abort's crossing to the proxy and the ending's return together take less than the allowance.\
The client half writes at most one `abort` for a request: when the caller's signal fires once the invocation is written, as for any invocation, and, for an invocation written with `parts` true, when it ends it without reading its `end` while its connection is open - `hop-stalled` - so the proxy's call is cancelled rather than left running; a client half that closes its connection writes no `abort`, since the proxy aborts the invocations in parts of a closed connection (`PX6`).\
Tested by: `E17`, in `test/contract/proxied-invocation.test.js`, with the whole wire record of two calls alike but for their `service`, reaching two endpoints over one proxy, an input making a request message of exactly 16777216 bytes and one of a byte more, another call in flight and a small one after each, a hop delayed in each direction, preparing that takes part of the bound, a find of several pages whose connection is lost between pages, the wall clock stepped forward and back while a call is in flight, the largest bound, the deadline sent for the default allowance, for an application's own allowance, and for bounds of 99, 100, 101, 2 and 1 milliseconds, whose allowances are 49, 50, 50, 1 and 0, the bound of 2 also with an application allowance of 0, each run to its ending as well as checked on the wire, and an allowance of 0 and of 1000, each run to its ending; every case records the direct call the proxy made - its moment, bound and abort - and checks the ending against it, with returns taking just less than the allowance, exactly the allowance and just more, at whole and fractional milliseconds - including a return longer than the allowance that is still read before the client half's deadline, its ending taken unchanged, after a timeout decided at a floored deadline and after an early answer - an answer, a refusal, a rejection and a delivery report observed at or after the proxy's call's deadline before its own timer has run, each losing to that deadline, and a find of 100 milliseconds whose later page is handed on with 80 milliseconds gone, its transmitted deadline and its ending checked, and an abort crossing the hop while the send is held for admission, arriving before and after admission; an abort before the send is admitted, which ends `not-delivered` with `agpCode` `ABORTED`, and one after, which reaches the host as a `cancel`, the call ending as the host's end then decides; and a deadline passing while the client half checks an invocation, prepared and unprepared, with a sendable and an unsendable input, and at the deadline exactly, each ending `unknown` with `bound-passed`, its attempt identity, `agpCode` and `deliveryReport` `null`, and nothing written, beside a check finishing before the deadline, which refuses `not-sendable` exactly; and `D4-E6`, in the same file, with a controlled clock: a call accepting parts whose request, holding that `aliveWithinMs`, is exactly 16777216 bytes, written and handed on, and one of a byte more refused `not-sendable` with nothing written, prepared and unprepared; `parts` written true exactly when `onPart` is given; parts arriving at the client half in order, each given to `onPart` deeply frozen and synchronously as it is read; the proxy writing `alive` at half its call's bound without parts, counted on from each `part` and `alive` it wrote, one from a timer that woke late, at 1 millisecond for a call bound of 1 and none once the call's ending is sent or its connection closed; the client half's deadline moved by each `part` and `alive` read before it, and not by one read at or after it with its timer held; an abort read before an `alive` the proxy already wrote, the invocation then ending as the proxy's call ends, an abort after which the proxy keeps writing `alive` and its call never ends, the invocation ending `hop-stalled` exactly one bound after the abort; and a hop that falls behind - the proxy's `alive` held in transit, and in turn its timer woken late, past the client half's deadline, without and with an abort before - the invocation ending `hop-stalled` there and the ending of the proxy's call, read later, discarded; `abort` after admission reaching the host as a `cancel`, for a whole call and a call in parts; one `abort` on the wire for an invocation in parts whose signal fires and whose deadline then passes, one for one ending `hop-stalled` with no signal, none for an abort after its ending, and none when the client half closes its connection, the proxy then aborting its call; and the proxy's `alive` stopping once a call's ending is dropped, its caller's result malformed.

**PX6 - How a proxied invocation ends.**\
An invocation the client half's own checks end (`PX5`) - refused `not-sendable`, or `unknown` with `bound-passed` because its deadline passed while checking - meets none of the events below, which follow those checks.\
The first of these events decides the ending, and nothing after it changes it:

| Event | Ending |
|---|---|
| No proxy has answered `welcome` by the connect deadline, and nothing of the invocation was written | `not-delivered`, with `proxyCode` `proxy-unreachable` |
| The proxy answers `refused` | `not-delivered`, with `proxyCode` the refusal's `code` |
| An `end` message for the invocation | its ending, unchanged |
| After any byte of the `invoke` message was written, the channel closes or carries a malformed line | `unknown`, with `reason` `proxy-lost` |
| The client half's own deadline passes before it has read the invocation's `end` - the proxy has not produced it, or the hop has not carried it | `unknown`, with `reason` `hop-stalled` |

A channel that closes after `welcome` and before any byte of an invocation is written is no proxy at all, and the client half connects and launches again until the connect deadline.\
An ending the client half or the proxy decides carries `attempt` `null`, since no attempt of the call layer is known - apart from the two endings of the client half's own checks, which carry the attempt identity it made, as the call layer's caller's do - and the ending of preparing alone carries the invocation and operation only where the caller gives them; a proxy whose caller throws, rejects, returns a non-native thenable, or settles to a value that is not a valid ending of the call layer (`readCarriedEnding` over `readCallEnding` and `readRefusalRecord`, zorg's `D54`, `D55`) observes any native promises in what was thrown or returned through `observePromises`, finishes that invocation's local bookkeeping, keeps the connection open, and sends nothing for that invocation, so the client half's deadline ends it `hop-stalled` (whereas a malformed line on the channel still closes the connection and yields `proxy-lost`).\
A `not-delivered` ending of the call layer carries `proxyCode` `null`; one of the proxy carries `agpCode` `null`, and the three an `end` can carry are `deadline-passed` (`PX5`), `proxy-stopping` (`PX7`), and `admission-refused` (`PX9`, when `ProxyHalfOptions.invocationRefusal?.()` returns `"admission-refused"` on an arriving `invoke` while no hub session is adopted and the presenter adjacency's committed `credential.phase` is `"issuer-refused"`, with nothing handed on), each with `attempt` `null`, which the client half takes unchanged and reads, as it reads the call layer's, through `readCarriedEnding`; an `unknown` ending the client half decides carries `agpCode` `null` and `deliveryReport` `null`, since the call layer's delivery reports stay with the proxy.\
The client half's deadline is a moment on its clock: an `end` read before it wins, and an `end` read at or after it is discarded, whichever runs first, the timer or the read.\
The rows above that end an invocation by the proxy's own code or by `proxy-lost` take precedence over `hop-stalled`, which ends only an invocation that nothing else has ended by the client half's deadline.\
For an invocation written with `parts` true, the client half's deadline is its deadline on signs of life (`PX5`), so `hop-stalled` says that no `part`, `alive` or `end` of it was read in time; the table is otherwise unchanged.\
So an invocation ends as `PX5`'s rule says whenever the proxy's call's ending is read before the client half's deadline - one that runs out its bound ending `unknown` with `bound-passed` and the call layer's delivery report, up to the allowance plus less than 1 millisecond early - and an invocation whose ending the proxy has not produced, or the hop has not carried, by that deadline ends `unknown` with `hop-stalled`, where nothing more is known; a delay longer than the allowance does not by itself mean `hop-stalled`, since an ending decided early can still arrive in time.\
An abort sent across the hop changes the ending only as the call layer decides it, never by the client half alone, but for an invocation in parts, whose deadline the abort bounds (`PX5`).\
When a short-lived process goes, the proxy finishes its calls and drops their endings, and never repeats an invocation.\
When a client's connection closes, for whatever reason, the proxy fires the abort signal of each invocation written with `parts` true that it carried for that connection, so its call is cancelled rather than left running, and still drops its ending; a whole call is finished as before.\
On a machine, the proxy keeps at most 33570816 bytes unwritten on one connection - twice `PX4`'s longest line - counting what it handed the socket that the operating system has not yet taken; a message whose writing would exceed that is not written, and the connection is closed at once, what it held unwritten discarded, so the proxy aborts its invocations in parts as above; the client half reads whatever the operating system had already taken, as ever, and then ends every invocation written on it and still undecided `proxy-lost`, the parts already given to `onPart` standing.\
For `client.status(options)` (`PX5`, zorg's Delta 8, `BL18`), the client half reads `clock.nowNs()` first (`start`), validates `options` (a non-null object, else rejects with `TypeError`), reads `options.timeMs` once (a finite number `>= 0` and `<= 2147483647`, else rejects with `RangeError`), and reads `options.signal` once (`undefined` or an `AbortSignal`, else rejects with `TypeError`; if `signal.aborted` is true, rejects with `signal.reason` with nothing connected), observing any thrown option-getter error through `observePromises`; it computes `deadline = start + BigInt(Math.floor(timeMs * 1e6))`, and if `clock.nowNs() >= deadline` after checking, resolves `Object.freeze({ state: "unreachable", proxyCode: "deadline-passed" })` with nothing connected; otherwise it arms its deadline timer (re-checking `clock.nowNs() < deadline` on an early wake) and `signal` abort listener before calling `connector.connect(handlers, { status: true })` once without ever calling `connector.launch()`: if `signal` fires before settlement, it closes any acquired link and rejects with `signal.reason`; if the deadline passes before settlement or `connect` throws or rejects, it closes any acquired link (including one arriving from a late `connect` after settlement, closed without writing) and resolves `Object.freeze({ state: "unreachable", proxyCode: "proxy-unreachable" })`; `{ kind: "absent" }` before the deadline resolves `Object.freeze({ state: "stopped" })`; `{ kind: "unsafe" }` before the deadline resolves `Object.freeze({ state: "unreachable", proxyCode: "runtime-dir-unsafe" })`; and `{ kind: "connected", link }` writes `{ operationProxy: 1, type: "status", key }`, where a valid `status` reply read before the deadline closes `link` and resolves `Object.freeze({ state: "running", ready, connections, inFlight, target })` (deeply frozen), a valid `refused` reply closes `link` and resolves `Object.freeze({ state: "unreachable", proxyCode: code })`, and any other or malformed message or `link` closing before a reply closes `link` and resolves `Object.freeze({ state: "unreachable", proxyCode: "proxy-unreachable" })`.\

**PX7 - Idle ending and stopping on a machine.**\
A proxy is idle while no connection is open and no call is in flight; when its idle timer of the application's idle time, from 1 second to 24 hours, fires, it checks again once the connections the operating system has already accepted are taken, and stays if a connection is open or a call is in flight.\
`ProxyHalf` tracks welcomed and waiting client connections in `conns` (whose size `half.connections()` reports) and newly accepted pre-`hello` connections separately in `helloConns`, and retains `idleDeadlineNs` across pre-`hello` connections (zorg's Delta 8, `BL18`): whenever `conns.size === 0 && inFlight === 0` is reached (whether or not `helloConns` is empty), if `idleDeadlineNs === undefined` it establishes `idleDeadlineNs = clock.nowNs() + msToNs(idleMs)` at once; while `helloConns.size > 0`, `idleTimer` is suspended without clearing `idleDeadlineNs` (so an accepted connection still prevents idle expiry while open), and when the last connection in `helloConns` closes without ever sending a valid `hello` (because it sent `status`, was refused `version` or `key-mismatch`, sent a malformed line, or closed empty), removing it from `helloConns` arms `idleTimer` for the retained `idleDeadlineNs` (expiring on the next turn if `clock.nowNs() >= idleDeadlineNs`) rather than `now + idleMs`; only when a connection sends a valid `hello` and moves from `helloConns` into `conns` (or when a call is in flight) is `idleDeadlineNs` cleared, so the next transition to `conns.size === 0 && inFlight === 0` after real client activity establishes a fresh `now + idleMs` deadline.\
An invocation in parts in flight is a call in flight, so it keeps the proxy from idling, and its idle timer runs again once no call is in flight and no connection is open.\
On `SIGTERM` or `SIGINT` the proxy stops accepting invocations - an `invoke` read after it is answered `end` with `not-delivered`, `proxyCode` `proxy-stopping`, `agpCode` and `attempt` `null`, and nothing handed on - and fires the abort signal of each invocation in parts in flight, whose call then ends within its bound after the abort (`EM12`).\
Otherwise, and on `SIGTERM` or `SIGINT` once each call in flight has ended within its bound and its ending has been sent, it stops accepting connections, closes those not welcomed and then, their calls having ended, those welcomed, closes and removes the channel socket, stops its caller, and releases its ownership lock on `<digest>.lock` last, then exits with status 0.\
Closing a welcomed connection hands on what was written to it first, waiting at most 2 seconds for every connection, after which those still open are destroyed, what they held unwritten discarded; stopping the caller is the application's, which the proxy awaits unbounded, so the time from `SIGTERM` to exit is the calls' time, at most 2 seconds of closing, and the caller's stop.\
A step that fails - closing the channel's server, removing its socket, releasing ownership, or an observer that throws - does not stop the later steps, which still run, and makes the status the proxy stops with 1, its exit status, which is the only record of the failure, since a launched proxy's output is discarded (`PX3`); ownership is released by its own step, or, when that step fails, as the process exits straight afterwards, when the operating system frees it (`PX3`); a caller that fails to stop leaves the status as it was, since nothing of the channel or ownership depends on it.\
A start that fails after taking ownership - an observer that throws at `owned` or `listening` included - closes what it had opened, the channel's server and then ownership, before its failure is given, so a later start, in the same process or another, owns the key.\
A client whose connection closes before `welcome` treats it as no proxy (`PX6`), and the next owner can only take the key after the last step.\

**PX8 - The browser adapter (`D57`).**\
In a browser, the client half reaches a shared worker created from the application's worker script with the name `operation-proxy:<digest>`, through one message port per page, carrying `PX4`'s messages as objects; there, since a page and a worker share no clock, `deadline` is instead the milliseconds left until `PX5`'s sooner deadline at the moment the page posts the message, by the page's `performance.now()`, and the worker's call is bound by that many milliseconds from the moment it receives the message, by its own `performance.now()`, rounded down as `PX5` says; so each side reads only its own clock; the worker's call's deadline is then its receipt plus that remaining time floored, which can be the outbound transit plus less than 1 millisecond later than a machine's would be, and its ending reaches the page in time whenever the outbound and return transits together take less than the allowance, which a browser application chooses to cover them; a message delayed past the page's deadline may still start its call, whose ending the page discards, having ended the invocation `hop-stalled`, which says the operation may have run; and a message whose remaining time at posting is a whole millisecond or more is admitted however late it arrives, while one with less is refused `deadline-passed`; with one more type for this adapter only: `{"operationProxy": 1, "type": "ping"}`, sent by each side every 5 seconds from the moment the port connects (before and after `welcome`, and accepted by both sides in either state), since a message port reports no closing; a side that hears nothing from the other for 15 seconds treats it as gone, and a page then ends its written invocations `unknown` with `proxy-lost`.\
The browser adapter carries `parts`, `part` and `alive` as the machine adapter does (`PX4`, `PX5`), each side keeping time on its own clock: the worker writes `alive` on its clock, from the bound it floored, and the page moves its deadline on signs of life on its own.\
Since a message port reports nothing written or unread, the page posts `{"operationProxy": 1, "type": "taken", "request"}`, with the part's `sequence` added for a part and `request` alone for an `alive`, once it has read each `part` and `alive` of a request it wrote - a part once given to `onPart`, or discarded - and the worker counts the bytes, as JSON in UTF-8, of each `part` and `alive` it posts on a port until its `taken` arrives; a `taken` answers the oldest `part` or `alive` of its request not yet taken, and one that answers none, or names a `sequence` other than that part's, breaks `PX4`'s table and closes the port.\
A post that would make that count exceed 33570816 bytes, twice `PX4`'s longest line, is not posted, and the port is closed at once, its invocations in parts aborted as on a machine (`PX6`); the page, which learns nothing of the close, still reads what the worker posted before it, as ever, and ends each invocation written on it and still undecided `hop-stalled` at its deadline or `proxy-lost` once it has heard nothing for 15 seconds, whichever comes first.\

The package `@apnex/operation-proxy` exports `createProxyClient` and `createProxyHalf`, the two halves over any channel and clock, `callClockOf`, `keyDigest`, `CHANNEL_LIMITS` and `DEFAULT_HOP_ALLOWANCE_MS`, and imports no module particular to one runtime; `@apnex/operation-proxy/machine` exports the machine adapter for Linux, `createMachineClient`, `startMachineProxy` and `runMachineProxy`; and `@apnex/operation-proxy/browser` exports the browser adapter (`PX8`), `createBrowserClient` and `runBrowserProxy`, as `export-map.json` records.\
It depends on `@apnex/operation-call` and `@apnex/shape-check` through their release files, and its tests on AGP's packages through `file:` links to an AGP checkout beside it.

## Fit criteria

### Does my project want this at all

- Short-lived processes in your system invoke named operations, and each is about to join the delivery beneath on its own.
- Many processes of one identity run on one host - a machine or a browser - sometimes at once.
- A process must still tell "it failed" from "it may have happened", even though its call crosses an extra hop.

### Does it meet my requirement

- Code written against the call layer runs through the proxy unchanged.
- The proxy starts when first needed and ends when idle, with nothing for a user to set up (`PX2`).
- Every invocation ends exactly once, and "unknown" is reported rather than guessed.

**It is the wrong tool when**

| You need | Reach elsewhere, because operation-proxy is |
|---|---|
| your processes long-lived anyway | unnecessary: embed the call layer directly |
| calls from other machines | not a network service |
| one connection shared by several identities | one identity per proxy |
| calls that survive a restart, or are retried for you | not a store and not a retrier |
| a decision about who may call what | not an authority |

## Adjustment policy

Internal and sovereign, so a fit gap has somewhere to go.

1. Record a measured gap where both sides can see it.
2. Resolve it by adjusting operation-proxy, so every consumer gets the change, or by fracturing it when the gap reveals a second duty.
3. Never fork.

The delivery beneath is reached through the call layer, so a new delivery layer needs no change to operation-proxy.

## Edges

**Composes:** nothing registered.\
Its proxy process and client half are halves of one duty, not separate components.

**Consumes, through a declared contract:**

- `operation-call`: `honest-call-ending`, `caller-chosen-bound`, `invocation-identity`, `request-correlation`, `call-refusal`, `answer-in-parts`, `cancel-invocation`
- `shape-check`: `plain-json-value`

**Composed-by:** nothing yet.\
Its first consumer, once built, is zorg's command-line client.

The registry's edge vocabulary has no edge for one component using another's contract without containing it; see the note in operation-call's entry.
